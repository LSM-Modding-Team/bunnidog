## QUICK INDEX — read this BEFORE you research anything (update it in the same session whenever you look something up)
Past sessions re-verified the same handful of names more than once (`mobInteract`, `putInt`, `registerItem`, `rarity`, the recipe format...). This index exists so that does not happen again.
**Rule:** if you had to look an API or a file format up, add a row to the table below (what, status, exact place) before you finish the session. Older per-session sections (now in docs/history/API_HISTORY.md) are the
history; this index is the map. `grep -n "name" docs/API_NOTES.md` finds any name in both.

Status words: **COMPILED** = the user's compile accepted it (names and types are right; runtime behaviour may still be open). **SOURCE** = seen in the real NeoForge sources/data, not compiled yet.
**ASSUMED** = written from memory of 1.21.x, nothing confirms it. **AVOIDED** = never seen anywhere, so our code does not use it.

### Research playbook (in this order)
1. Grep this file. 2. If it is not here, sparse-clone NeoForge 26.2.x (about 30 s, 33 MB; bash can reach github.com in most sessions, check first):
   `mkdir nf && cd nf && git init -q && git remote add origin https://github.com/neoforged/NeoForge && git config core.sparseCheckout true && printf 'tests\npatches\nsrc\n' > .git/info/sparse-checkout && git fetch -q --depth 1 origin 26.2.x && git checkout -q FETCH_HEAD`
3. What the clone has and what to use it for:
   * `tests/src/main/java/...` = real mod code calling the API. Best source for "how is this used" and for exact import lines (`grep -rl "import net.minecraft.world.InteractionHand;" tests src patches`).
   * `tests/src/generated/resources/data/...` = REAL 26.x data JSON (recipes, tags, loot tables, ...). Best source for data file formats.
   * `src/main/java/net/neoforged/neoforge/...` = NeoForge's own classes, e.g. every `DeferredRegister` overload (`registries/DeferredRegister.java`).
   * `patches/net/minecraft/...` = DIFFS on vanilla classes. They show the signature and visibility of a method only when NeoForge changed it or it sits within 3 lines of a change
     (`patches/net/minecraft/world/entity/animal/sheep/Sheep.java.patch` shows `public InteractionResult mobInteract(Player player, InteractionHand hand)`). Vanilla method BODIES are not there.
   * It does NOT contain vanilla sources, so a vanilla-only name (`isInLove`, `Attributes.JUMP_STRENGTH`, `Shapes.box`...) cannot be confirmed from it; grep simply finds nothing.
4. Grep class DECLARATIONS, not names: javadoc in NeoForge still uses old names (`BlockEvent.BreakEvent` is now `BreakBlockEvent`). `grep -rn "class .*Break.*Event" src`.
5. No network? `web_search` + `web_fetch` on docs.neoforged.net (26.1 pages) and the porting primers `https://raw.githubusercontent.com/neoforged/.github/main/primers/26.1/index.md` (also 26.2, 26.3).
6. A vanilla-only name nobody can confirm: write it the 1.21.x way, list it as ASSUMED in that session's section, tell the user, and let their compile settle it (this is how every vanilla name below was
   settled). Better: design around it. Phase 4e needed "is this animal in love?", `isInLove()` was never seen anywhere, so the love state is tracked by our own `GuavaMemory` instead.

### Traps that cost time before
* The javadoc of NeoForge lags behind its code (old event names). Trust class declarations and `import` lines.
* `registerGoals()` runs inside the super constructor, before any field initializer of the subclass (see `docs/REFERENCE.md` "Conventions"). Fields with initializers are fine for state the super constructor never touches (`Bunnidog.guavaMemory`).
* A compile proves the names and types, not the behaviour or data files: JSON (recipes, models, tags, blockstates) is only validated when the game loads it. Every data file the mod adds is listed as "open" until the user has run the game.
* `tools/GenomeCheck.java` methods must not name a local variable `java` (it hides the `java.util` package); `compact()` strips ALL whitespace, so do not use it for text that has spaces in it (a lang value).
